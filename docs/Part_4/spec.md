# 系统提示工程化 Spec

## 背景

PseudoClaude 已经完成了多 provider 流式对话、本地工具系统和 Agent Loop。模型现在能在一次用户请求内多轮“推理 → 调工具 → 看结果 → 继续推理”，也支持计划模式与执行模式。

当前的全局系统提示仍然是一段很短的固定文本，把身份、行为方式和输出格式揉在同一块常量里。它能让系统“能干活”，但缺少结构、优先级和可扩展位置；后续想加入新类别指令，只能继续往字符串里追加。与此同时，每轮请求都会把稳定不变的系统提示和工具定义重新发送，动态环境信息又没有被系统化注入，模型对当前工作目录、平台、日期、git 状态、应用版本和当前模型等上下文缺少稳定认知。计划模式提醒也仍然混在普通请求文本或系统提示附近，注入频率不可控。

本章要给 PseudoClaude 做系统提示工程化：把全局指令拆成按职责划分、按优先级拼装的模块；把稳定内容与变化内容分到可缓存通道与消息通道；引入带特殊标签的补充消息注入机制，在运行中注入指令而不污染缓存、不被模型当作用户提问；让会话级开关按轮次频率注入。目标是让 PseudoClaude 从“能干活”进一步变成“干得好、稳得住、成本可观测”。

## 目标

- 把全局指令拆成按职责划分的模块，并按优先级拼装成完整系统提示；新增一类指令时只需挂载新模块，不改装配主逻辑。
- 区分稳定与变化内容：稳定系统模块与工具定义走可缓存通道，环境信息、补充提醒和对话历史走不缓存的消息通道。
- 在工具描述与系统提示中双重强化关键约定，提高模型对“优先用专用工具”“编辑前必先读”“验证前不声称成功”等规则的遵守率。
- 提供带特殊标签的补充消息注入机制，让运行时补充指令既不污染缓存，也不会被模型当成用户输入来直接回复。
- 会话级开关的提醒按轮次注入：首轮完整、间隔轮次重复完整、其余轮次精简，控制注入频率与上下文成本。
- 从 provider 返回的用量信息中解析缓存写入与缓存读取信息，用于验证缓存策略是否真实生效。
- 准备一组典型人工对比场景，定性观察新提示对关键行为的改善。

## 功能需求

- F1: 模块化系统提示拼装
  系统应把稳定的全局指令按职责拆成模块。每个模块具备名称、优先级和内容。装配时按优先级从高到低拼接成完整系统提示，模块之间以空行分隔。固定模块七个，按优先级排列为：身份、系统约束、任务模式、动作执行、工具使用、语气风格、文本输出。

- F2: 可选模块预留
  系统应在固定模块之后预留三个可选模块位置：自定义指令、已激活 Skill、长期记忆。本章不接入这些内容的真实来源；当内容为空时应自动跳过，不留下多余空行。后续新增模块时，只需定义模块并挂到对应优先级，不改装配主逻辑。

- F3: 环境信息构造与呈现
  系统应收集运行环境信息，构造成供模型理解当前上下文的文本。环境信息至少覆盖工作目录、操作系统或平台、当前日期、git 状态、应用版本、当前 provider 和当前模型。环境信息作为稳定系统提示之后的独立系统级内容块呈现，并与可缓存稳定模块物理分离。

- F4: 稳定内容走可缓存通道
  稳定不变的内容应归入可缓存通道，至少包括拼装后的稳定系统模块和稳定工具定义。变化内容应归入不缓存通道，至少包括环境信息、补充提醒、对话历史、当前任务文本和轮次状态。可缓存内容必须跨轮逐字节一致，不混入任何随轮次、时间、工作目录或任务变化的成分。

- F5: provider 缓存策略
  Anthropic provider 应对稳定系统模块和工具定义使用显式缓存标记或等价机制，使稳定前缀可被复用，环境信息与历史位于非缓存内容中。OpenAI provider 应把稳定内容保持在请求前缀，依赖端点的前缀缓存能力自动受益；当端点或兼容 base URL 不支持缓存字段时，系统仍正常运行。

- F6: 缓存命中解析
  系统应从 provider 响应用量中解析缓存写入与缓存读取信息，并随 token 用量一并对外暴露，供 smoke 或调试输出验证缓存策略。Anthropic 应解析缓存创建与缓存读取 token 字段；OpenAI 应解析缓存命中字段。provider 或兼容端点未返回缓存字段时，应按不可用或零值处理，不中断会话。

- F7: 关键约定双重强化
  系统应在全局系统提示和相关工具描述中同时表述关键约定，包括优先使用专用工具而不是临时拼凑命令、编辑文件前先读取相关文件、保护用户已有改动、只在合适模式执行有副作用动作、先验证再宣称完成。工具描述中的强化必须与工具真实能力一致，不得夸大能力或制造不可执行约束。

- F8: 工具描述稳定化
  工具定义应保留稳定的名称、能力说明、参数说明和安全边界。动态环境信息、当前任务内容、会话历史、临时模式文本或轮次状态不得写入工具描述，避免破坏缓存复用和工具语义稳定性。工具顺序也应稳定，避免同一工具集合在不同轮次生成不同前缀。

- F9: 补充消息注入机制
  系统应提供一种带特殊标签的补充消息形式，例如 `<system-reminder>`。构造请求时，运行时补充指令通过消息通道注入，让模型理解其为系统级补充上下文，而不是用户提问。此类消息每轮动态构造，不写入持久对话历史，不破坏缓存稳定前缀。

- F10: 历史合法性
  注入补充消息后，请求消息序列仍应保持 provider 可接受的角色顺序，工具调用与工具结果配对不得被破坏。补充消息不得写入持久历史，因此不影响后续轮次的恢复、取消后继续对话或工具结果配对。

- F11: 计划模式按轮次注入
  计划模式提醒应改由补充消息机制承载，不再拼到稳定系统提示尾部。系统应按 Agent Loop 轮次控制注入频率与详略：首轮注入完整提醒，之后每隔固定轮次重复一次完整提醒，其余轮次注入精简提醒。计划模式仍只开放只读工具；执行模式切回全工具，并基于最近一次相关计划继续执行。

- F12: 跨协议一致
  Anthropic 与 OpenAI provider，包括 OpenAI 兼容 base URL，应装配同一套模块化系统提示、环境信息和补充消息。两类 provider 在模块内容、注入时机、计划模式注入节奏、工具描述强化和缓存用量暴露方面应尽量保持行为一致；仅缓存标记和字段解析按各自协议能力适配。

- F13: 环境采集降级
  环境信息采集应快速、有界、可降级。git 状态、平台信息、版本信息或模型信息任一项取不到时，应省略或标注不可用，而不是阻塞界面或中断模型请求。环境信息不得包含 API key、敏感环境变量或其他凭据。

- F14: 人工对比场景
  系统应准备一组典型人工对比场景，用于比较旧提示与新提示的行为差异。场景至少覆盖只读规划、编辑前读取、优先使用专用搜索或文件工具、工具失败后继续推理、安全边界、输出风格、历史合法性和缓存命中观测。

- F15: 现有行为兼容
  新系统提示结构接入后，现有多 provider 流式文本、工具调用、Agent Loop、计划模式、执行模式、用户取消、工具结果回灌、token 用量事件和 TUI 展示应继续可用。对没有工具调用的普通聊天，不应出现内部标签、环境块或提示工程说明。

## 非功能需求

- N1: 缓存确定性
  可缓存块在同一会话多轮之间应逐字节稳定。模块装配顺序、工具顺序、空行规则和文本内容都应可预测，不依赖随机 map 顺序、当前对话长度或工具注册的偶然结果。

- N2: 缓存友好
  稳定系统模块和工具定义应尽量保持稳定，动态信息必须隔离，避免每轮请求都让大段稳定内容失去缓存价值。

- N3: 不破坏既有 Agent Loop
  Agent Loop 的多轮编排、流式双路收集、多工具保序回灌、只读工具并发、副作用工具串行、用户取消、错误恢复、用量事件和进度展示不得退化。

- N4: 历史合法性
  动态注入的补充消息不得导致 provider 拒绝请求，也不得破坏工具调用与工具结果的配对关系。取消、中断或下一轮继续对话后，持久历史仍应可用。

- N5: 环境采集性能
  环境信息采集应在短时间内完成，且失败可降级。涉及外部命令或 git 状态读取时，应有边界，避免显著拖慢请求发起。

- N6: 敏感信息保护
  环境信息、调试输出、用量输出和普通对话区均不得出现 API key、认证 token 或敏感环境变量。

- N7: 缓存字段解析健壮
  provider、模型或兼容端点未返回缓存字段时，系统按不可用或零值处理，不 panic，不因缺字段中断本轮或会话。

- N8: 可扩展性
  新增系统提示模块或补充提醒时应改动局部，不触及装配主逻辑，不改变 provider 对外抽象的语义稳定性。

- N9: 可测试性
  模块顺序、可选空槽跳过、稳定块字节一致性、环境信息隔离、补充消息不持久、计划模式注入频率、缓存字段解析和历史合法性都应能通过自动化测试或可重复的 smoke 场景验证。

- N10: 输出体验
  运行时补充标签和内部环境块不应泄漏到普通助手回答中。最终输出仍应清晰、简洁，并符合 PseudoClaude 的终端协作风格。

- N11: 项目规范
  改动应通过项目既有格式化、静态检查和测试要求；新增调试或 smoke 输出不得污染正常 TUI 体验。

## 不做的事

- 不加载项目级指令文件：自定义指令只是预留空槽，本章不从 AGENTS、CLAUDE、README 或其他项目指令文件读取内容。
- 不实现自动记忆：长期记忆只是预留空槽，本章不做记忆写入、存储、召回或更新。
- 不接入真实 MCP：已激活 Skill 只是预留空槽，本章不连接外部 MCP server，不读取 MCP 资源。
- 不做自动化评估框架：本章只做缓存字段解析验证和典型场景人工对比，不建批量评分、回归平台或自动判分。
- 不做历史增量缓存：本章只缓存稳定前缀，不对对话历史另打缓存断点。
- 不做缓存配置系统：缓存 TTL、断点数量和断点位置使用内置策略，本章不通过配置文件调整。
- 不把缓存命中放入状态栏：缓存信息只通过事件、smoke 或调试输出暴露，不进入 TUI 状态栏。
- 不做提示词热加载：模块内容内置于代码，不做外部模板文件、运行时热加载或模板语法。
- 不新增权限审批系统：安全边界通过提示、工具描述和现有工具安全性表达，不做逐工具用户确认。
- 不更换 provider API 或模型路由：沿用当前 provider 抽象、配置和模型选择策略，只扩展请求装配与用量解析。
- 不实现多模态或流式工具结果：沿用现有文本、工具调用和工具结果流程。

## 验收标准

- AC1: (F1) 查看生成的稳定系统提示时，可以看到身份、系统约束、任务模式、动作执行、工具使用、语气风格和文本输出七个固定模块，且模块按指定优先级排列、空行分隔。
- AC2: (F2) 自定义指令、已激活 Skill 和长期记忆内容为空时，装配结果自动跳过这些模块且不留下多余空行；填入占位内容时，它们出现在固定模块之后。
- AC3: (F3) 发起一次模型请求时，系统级环境信息包含工作目录、平台、当前日期、git 状态、应用版本、provider 和模型；该内容与稳定系统模块分属不同内容块。
- AC4: (F4) 连续两轮构造请求时，稳定系统模块与工具定义组成的可缓存块逐字节一致；故意改变工作目录、日期或用户任务时，可缓存块不变。
- AC5: (F5) Anthropic provider 在稳定系统模块和工具定义处使用显式缓存标记或等价机制；OpenAI provider 保持稳定内容位于请求前缀，兼容端点不支持缓存字段时请求仍可完成。
- AC6: (F6) provider 返回缓存相关用量字段时，事件、smoke 或调试输出能观察到缓存写入 token 与缓存读取 token；OpenAI 返回 cached tokens 时能被解析，未返回时显示不可用或零值且不报错。
- AC7: (F7) 检查稳定系统提示和文件、搜索、命令等相关工具描述时，“优先使用专用工具”和“编辑文件前先读取”两类关键约定在两处都有表达。
- AC8: (F8) 改变当前任务文本、工作目录、日期或模式时，工具名称、工具说明、参数 schema 和工具顺序保持稳定。
- AC9: (F9) 注入的补充消息以特殊标签包裹；模型遵循其中的补充规则，但普通回答不会把标签当作用户提问回应，也不会复述标签本身。
- AC10: (F9, F10) 补充消息不会写入持久对话历史；注入后 provider 请求不因角色顺序或工具结果配对问题失败。
- AC11: (F11) 在计划模式多轮循环中，首轮注入完整提醒，达到配置间隔的轮次重复完整提醒，其余轮次注入精简提醒；计划模式只开放只读工具，执行模式切回全工具。
- AC12: (F12) 使用 Anthropic 与 OpenAI provider 分别运行普通聊天和工具调用任务时，二者都能接收到同一套稳定系统提示、环境信息和补充消息，并保持等价行为。
- AC13: (F13) 在非 git 目录、git 不可用或版本信息缺失时，环境信息对应项降级为省略或不可用，界面不卡住，请求仍正常发起。
- AC14: (F14) 人工对比场景文档包含至少八类场景：只读规划、编辑前读取、优先工具选择、工具失败恢复、安全边界、输出风格、历史合法性和缓存观测；每个场景都有输入、观察点和预期差异。
- AC15: (F15) 现有普通聊天、Agent Loop 多轮工具调用、用户取消、工具错误恢复和历史继续对话仍可运行；普通回答不会输出内部标签、环境块或提示工程说明。
- AC16: (N6, N11) 项目既有测试、格式化和静态检查通过；对话区、调试输出和环境信息中没有 API key 或认证 token 明文。
