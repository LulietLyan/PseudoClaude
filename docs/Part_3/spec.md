# Agent Loop Spec

## 背景

PseudoClaude 已经具备多协议流式对话能力，并在上一章加入了本地工具系统。模型现在可以请求工具，程序也能执行工具并把结果回灌到会话历史中。

当前限制是：一次用户请求中，模型只能“请求工具 → 等待程序执行 → 本轮停止”。如果工具结果显示还需要继续查看、修改或运行验证，用户必须手动再次催促模型继续。这让 PseudoClaude 仍然像一个被动聊天客户端，而不是能围绕目标自主推进的 Agent。

本章要在现有工具系统之上加入 Agent Loop：系统在一次用户请求中循环执行“模型推理、工具调用、工具结果回灌、继续推理”，并通过异步事件流把 Agent 内核与界面展示解耦，直到任务自然完成或触发停止条件。

## 目标

- 让一次用户请求可以驱动多轮模型推理与工具执行，形成 ReAct 风格的自主循环。
- 为循环提供明确停止条件，避免无限执行或异常状态卡死。
- 用统一异步事件流表达文本、工具调用、工具结果、token 用量和进度，让界面不直接依赖循环内部实现。
- 在流式接收时同时满足实时展示和完整响应收集，既让用户看到即时文本，也让循环能判断下一步。
- 当模型一次返回多个工具调用时，按工具安全性分批执行：可并发的并发执行，有副作用的按顺序执行。
- 提供 Plan Mode 两段式工作流：`/plan` 只开放只读工具并生成计划，`/do` 基于上一轮计划切换到全工具执行。

## 功能需求

- F1: ReAct 循环
  系统在一次用户请求内支持多轮循环。每一轮先请求模型并接收流式响应；如果响应中包含工具调用，则执行工具、把结果回灌到会话历史，并自动进入下一轮；如果响应不再包含工具调用，则把模型最终文本作为本次任务结果并结束。

- F2: 循环状态隔离
  每次用户提交都会创建独立的 Agent 执行上下文。该上下文记录本次请求的原始目标、循环轮次、已产生文本、工具调用、工具结果、停止原因和用量信息。本次上下文结束后，界面回到可输入状态，并且后续用户请求能继续使用已回灌的会话历史。

- F3: 停止条件
  Agent Loop 必须支持并区分以下停止条件：
  1. 模型完成最终回答且不再请求工具。
  2. 达到配置的最大迭代次数。
  3. 用户取消当前执行。
  4. 连续请求未知工具达到限制。
  5. 模型流式响应或 provider 调用出错。
  触发任一停止条件时，系统应结束本次循环，保留已完成的历史回灌，并向界面报告可读的停止原因。

- F4: 最大迭代兜底
  系统必须有默认最大迭代次数，并允许调用方配置。达到上限时，不再继续请求模型；界面应看到“达到迭代上限”的状态，而不是静默停止或继续执行。

- F5: 未知工具连续限制
  当模型请求不存在的工具时，系统把未知工具作为结构化工具错误回灌给模型，使模型有机会自我修正。若连续未知工具次数达到限制，则停止循环并报告原因。成功执行任意已知工具或模型输出最终回答后，连续未知工具计数清零。

- F6: 用户取消
  用户取消当前任务时，系统应停止接收模型流、停止或取消尚未完成的工具执行，并结束 Agent Loop。已经完成并回灌的消息保留；未完成的工具结果不得伪装成成功。

- F7: 异步事件流
  Agent 内核通过统一事件流向外发布进展。事件至少覆盖：文本增量、助手完整文本片段、工具调用开始、工具调用完成、工具结果、token 用量更新、循环轮次或阶段进度、停止原因、错误。界面只消费事件并更新展示，不直接控制循环内部步骤。

- F8: 流式双路收集
  每轮模型流式响应都同时走两条路径：文本增量实时发布给界面；完整响应内容被收集起来，供循环在该轮结束后判断是否有工具调用、是否需要继续、以及需要追加什么历史。实时展示不得破坏完整响应收集，完整收集也不得阻塞文本增量发布。

- F9: 多工具调用处理
  当模型在同一轮中返回多个工具调用时，系统应收集完整调用列表并全部处理，而不是只执行第一个。每个工具调用都必须有对应的工具结果或错误结果，并按 provider 要求回灌到会话历史。

- F10: 工具安全性分批
  系统根据工具的安全性或副作用等级对同一轮工具调用分批执行。只读、互不依赖且可并发的工具可以并发执行；会写文件、执行命令或产生副作用的工具必须按稳定顺序串行执行。批次执行顺序应可预测，避免并发副作用造成不确定结果。

- F11: 工具结果顺序
  无论工具实际执行是并发还是串行，系统回灌给模型的工具结果顺序必须与模型本轮请求的工具调用顺序一致，确保模型能稳定对应每个调用与结果。

- F12: token 用量事件
  当 provider 能提供 token 用量时，Agent Loop 应通过事件流发布输入、输出或总量信息。provider 不提供用量时，系统仍能正常运行，并通过事件表达“用量不可用”或保持该项为空。

- F13: 进度事件
  Agent Loop 应在关键阶段发布进度事件，包括开始执行、每轮模型请求开始、工具批次开始、工具批次结束、循环结束。进度事件应包含当前轮次和可读说明，便于 TUI 展示正在发生什么。

- F14: Plan Mode 入口
  用户输入 `/plan` 加任务内容时，系统进入计划模式。计划模式仍使用 Agent Loop，但只向模型开放只读工具；模型可以自主循环查看文件、搜索内容或读取上下文，最终输出计划并停止。计划模式不得执行写文件、改文件、运行命令等有副作用工具。

- F15: Plan Mode 执行接续
  当已有最近一次成功的计划模式结果时，用户输入 `/do` 可进入执行模式。执行模式应把上一轮计划、对应的原始任务和当前会话历史作为上下文，切换回全工具集合，并通过 Agent Loop 自主执行。执行结束后，该计划不应被错误复用到不相关任务。

- F16: 普通模式兼容
  用户不使用 `/plan` 或 `/do` 时，系统直接使用全工具 Agent Loop 处理请求。若模型不请求工具，行为应保持普通流式聊天体验：实时显示文本，结束后回到可输入状态。

- F17: 工具错误继续推理
  工具参数错误、工具执行失败、命令非零退出、工具超时等已知工具错误应作为工具结果回灌给模型。除非触发明确停止条件，Agent Loop 应允许模型基于错误结果调整下一步，而不是立即中断整个任务。

- F18: 界面解耦展示
  TUI 应通过消费 Agent 事件展示文本、工具状态、轮次进度、用量和停止原因。TUI 不应自行拼装 Agent Loop、直接执行工具或依赖 provider 细节。

## 非功能需求

- N1: 稳定性
  循环过程中出现 provider 错误、流式解析错误、工具错误、上下文取消、未知工具或达到上限时，程序不得崩溃或破坏终端状态。

- N2: 可控性
  最大迭代次数、未知工具连续限制和取消机制必须保证 Agent Loop 不会无限运行。默认限制应足够保守，适合本地终端交互。

- N3: 响应性
  模型流式接收、工具执行和循环调度不得阻塞界面渲染。长任务期间用户应持续看到进度或状态变化，并能取消。

- N4: 可观测性
  每一轮推理、工具调用、工具结果、停止原因和可用 token 用量都应可被事件流观察到，便于界面展示和自动化测试。

- N5: 确定性
  同一轮多个工具调用的分批规则和结果回灌顺序应稳定，避免由于并发执行导致历史顺序随机变化。

- N6: 向后兼容
  已有 provider 配置、纯文本聊天、工具定义转换、工具参数校验、工具结果回灌和 TUI 基本输入输出行为应继续可用。

- N7: 可测试性
  循环停止条件、双路流式收集、多工具分批、Plan Mode 只读限制、`/do` 接续执行和取消行为应能通过自动化测试或可重复的集成场景验证。

## 不做的事

- 不实现权限系统：本章不做逐工具、逐命令、逐路径的用户交互式确认。
- 不实现上下文压缩：循环历史增长不做摘要、裁剪或长期记忆管理。
- 不实现用户交互式追问：Agent Loop 中途不暂停向用户提问并等待回答。
- 不接入 MCP：本章只使用上一章已有本地工具，不连接外部 MCP server。
- 不实现工具市场或动态插件：工具集合来自现有注册系统，不做运行时安装。
- 不实现复杂任务队列：一次只处理一个前台用户请求，不做后台多任务并发调度。
- 不做持久化计划库：`/plan` 的结果只用于最近一次相关 `/do`，不跨进程保存。
- 不做权限沙箱增强：命令和文件工具的基础边界沿用上一章能力，不新增系统级隔离。
- 不做上下文成本优化：token 用量只观测和展示，不据此自动压缩或降级模型。

## 验收标准

- AC1: (F1) 构造一个需要两次工具调用才能完成的任务时，用户只提交一次请求，系统能自动完成“模型请求工具 → 执行工具 → 回灌结果 → 再次请求模型”的连续流程，直到模型给出最终回答。
- AC2: (F2) 每次用户提交都有独立的执行上下文；本轮停止后界面恢复输入，下一轮请求能携带已回灌的会话历史继续对话。
- AC3: (F3) 分别触发最终回答、迭代上限、用户取消、连续未知工具和流式错误时，系统都能停止循环，并报告不同的可读停止原因。
- AC4: (F4) 将最大迭代次数设置为较小值时，循环在达到上限后停止，不再发起下一次模型请求，并显示达到上限。
- AC5: (F5) 模型连续请求未知工具时，前几次未知工具作为工具错误回灌；达到连续限制后循环停止。若中间成功执行已知工具，连续计数会清零。
- AC6: (F6) 用户取消正在运行的 Agent Loop 后，模型流或工具执行被取消，界面回到可输入状态，并且不会追加伪造成功的未完成工具结果。
- AC7: (F7) 使用测试事件消费者运行一次包含文本和工具的任务时，可以观察到文本、工具调用、工具结果、进度、停止原因，以及可用时的 token 用量事件。
- AC8: (F8) 流式文本能实时到达界面，同时循环结束后完整文本能被追加到会话历史；两者内容一致且没有丢字或重复。
- AC9: (F9) 模型同一轮返回多个工具调用时，系统会处理全部调用，并为每个调用回灌一个结果或错误结果。
- AC10: (F10) 同一轮包含多个只读工具调用时，它们可以并发执行；同一轮包含写文件、改文件或命令执行时，有副作用调用按稳定顺序串行执行。
- AC11: (F11) 即使只读工具并发完成顺序不同，回灌给模型的工具结果顺序仍与模型请求顺序一致。
- AC12: (F12) provider 返回 token 用量时，事件流中能观察到用量更新；provider 不返回用量时，任务仍正常完成。
- AC13: (F13) 长任务执行期间，界面能显示当前轮次、工具批次或阶段说明，而不是只有静止等待状态。
- AC14: (F14) 输入 `/plan <任务>` 时，模型可以调用只读工具收集信息并输出计划；若模型请求写文件、改文件或运行命令，系统不会执行副作用操作，而是返回不可用或不允许的工具结果。
- AC15: (F15) 在成功生成计划后输入 `/do`，系统能基于上一轮计划和原任务进入全工具执行模式；没有可用计划时输入 `/do` 会给出清晰提示而不是盲目执行。
- AC16: (F16) 普通文本聊天且模型不请求工具时，仍按既有流式体验展示文本并结束，不出现多余工具状态或循环错误。
- AC17: (F17) 已知工具返回参数错误、执行失败或超时时，错误结果会回灌给模型；未触发停止条件时，模型仍可继续下一轮修正。
- AC18: (F18) TUI 仅通过 Agent 事件更新展示；替换为测试事件消费者时，Agent Loop 仍可完整运行并被验证。
